## 第 1 页｜执行摘要
- 导语：面向甲方 SAP 负责人与模块顾问，回答“二次开发资产能否按时按质迁到 S/4”
- 迁移路径：S/4HANA 全新实施（Green Field），新建目标系统并按蓝图配置业务；本专项选择性复用有价值的 ECC 二次开发
- 按时：
  - 非增强对象：T0−3 周至 T0 完成基线搬运、必要技术适配和技术验收
  - 增强对象：T0 后识别与迁移，不计入前三周
  - 按项目蓝图方案产生的后续调整另行排期
- 按质（技术测试标准）：
  - 范围内对象及依赖已迁入、激活并核对清单
  - 程序语法检查无错误，按记录的入口/调用路径运行无 Dump
  - 函数、类等通过适当的调用入口验证，不能以“没有执行”代替通过
- 四个结论：范围可控｜完整性可核对｜技术迁移完成｜后续开发统一管理
- 交付边界：技术迁移完成说明程序已迁入且技术测试通过，不表示业务规则验证、集成测试、UAT 或上线工作已完成
- 投入判断：程序搬运与技术测试不是主要难点和工作量大头，后续按业务规则变化进行的调整、修改及业务测试才是主要投入
- 结论：本专项以工具化技术迁移快速复用存量程序，业务验证与上线由 S/4 实现项目统一管理

# 01 项目背景与总体方法

## 第 2 页｜项目背景与迁移策略
- 导语：Green Field 下不重新开发、不整体废弃，而是按需复用有价值的 ECC 二次开发
- 背景三问：现状（为什么迁移）｜冲突（面临的关键问题）｜出路（如何解决），对应以下三条：
  - 迁移路径：S/4HANA 全新实施，新建目标系统并按项目蓝图配置业务；本专项选择性复用有价值的 ECC 二次开发。数据迁移范围与历史查询/留存方案另行确认，旧 ECC 退役以查询与运行承接条件满足为前提
  - 复用原则：能保留的现有实现尽量保留，优先完成影响 S/4 运行的必要适配；不把全面改写 CDS/RAP/Fiori 或全面增强拆分作为迁移前提，后续优化按业务收益另行安排
  - 实施节奏：非增强对象在蓝图汇报前三周完成基线搬运、必要技术适配和技术验收；增强识别与迁移在蓝图汇报后进行，按项目蓝图方案产生的后续调整另行排期
- 三种迁移方式：
  - 重新开发：不作为本项目的迁移方式
  - 废弃：不作为本项目的迁移方式
  - 按需迁移：本项目采用的迁移策略
- 工作重点：本项目以工具化技术迁移快速复用存量程序；程序搬运与技术测试不是主要难点和工作量大头，后续按业务规则变化进行的调整、修改及业务测试才是主要投入，统一纳入 S/4 实现项目开发管理；具体投入以项目数据计量，不预设比例
- 工具与方法：自研工具 YMIR / YENH 搬运与治理；SAP 官方工具栈（Readiness Check / ATC / Custom Code Migration）评估适配
- 交付边界：技术迁移完成说明程序已迁入且技术测试通过，不表示业务规则验证、集成测试、UAT 或上线工作已完成
- 结论：按需迁移把投入集中在“必要适配”，把业务优化留给后续项目按收益安排

## 第 3 页｜迁移生命周期（SAP Activate 阶段映射）
- 导语：时间基准为 T0；三周窗口为 T0−3 周至 T0；依据蓝图方案的后续调整不计入这三周
- 时间/阶段 × 业务线（业务顾问）｜技术线（技术顾问）｜交付节点：
  - 三周窗口前（Discover/Prepare 及项目准备）：确认现有用途、非增强对象范围与责任人｜工具/RFC/目标环境就绪、源版本核对、非增强对象清单及 ATC 初评准备｜非增强基线、执行条件和资源到位
  - T0−3 周至 T0（蓝图汇报前）：并行完成蓝图方案与汇报准备｜非增强对象依赖核对、YMIR 分批搬运、激活、ATC 检查、必要技术修复和差异对账｜非增强对象基线迁移在三周内完成
  - T0 之后（增强技术迁移）：确认增强用途与目标去向｜YENH 增强识别 → 策略确认 → 技术迁移 → 语法检查/运行无 Dump｜增强技术交付，不计入前三周
  - 各技术迁移批次完成后：确认交接责任｜保存对象/版本及技术测试记录，完成批次交付；各批次可分别封存，全部范围交付后封存专项清单｜技术迁移生命周期结束
  - S/4 实现项目后续阶段（背景）：业务测试、业务规则确认｜业务调整、后续测试问题及需开发的 ECC 增量进入项目开发清单，项目另行管理测试、UAT、上线与运维｜项目开发管理，不延长已封存迁移清单
- 三条工作线：非增强对象（三周窗口内完成并封存）｜增强对象（T0 后完成并封存）｜S/4 实现项目（持续开展，由 S/4 项目承接）
  - 技术迁移期间由迁移团队协调；各批次交付后由 S/4 实现项目承接
- 三周内的“完成”：范围内非增强对象及依赖已迁入、激活并核对清单，语法检查无错误，按记录的入口/调用路径运行无 Dump；函数、类通过适当入口验证；增强在蓝图后采用同一标准，不要求全部业务路径或业务结果已验证
- 三周内分工节奏：第 1 周依赖复核与分批搬运｜第 2 周语法/运行检查和必要技术修复｜第 3 周技术测试收尾、对账与交付；批次滚动并行；交付前发现语法错误或运行 Dump，修复后再确认技术测试通过
- 后续工作边界：交接后的测试问题、业务规则变化、蓝图调整均作为 S/4 项目开发清单中的开发项管理，不重新开启技术迁移清单，也不追溯累加迁移工作量
- 双线同步：技术迁移期间由迁移团队协调，交付后由 S/4 实现项目承接双线台账；清单封存不等于停止同步，配套资产按约定批次技术交付，不因后续业务使用无限延长迁移生命周期
- 注释：SAP Activate 阶段仅作背景映射；业务集成测试、UAT、上线由实现项目管理，不作为技术迁移完成或清单封存的前提
- 结论：两类对象分别在 T0 前后完成技术交付，后续工作由 S/4 实现项目承接

## 第 4 页｜迁移方法论总览
- 导语：六步适用于各自工作线，不表示所有对象同时识别、同时搬运
- 六步与交付物：
  - 范围确定 → 范围基线
  - 对象盘点与 ATC 初评 → 盘点结果清单 / 技术迁移清单
  - YMIR 分批搬运 → 批次差异报告
  - 语法/运行检查与必要技术修复 → 检查与修复记录
  - 技术测试（语法无错误、运行无 Dump）→ 技术测试记录
  - 交付与清单封存 → 交付封存记录
- 两条工具泳道：
  - 官方栈：Readiness Check / ATC / Custom Code Migration（用于评估与检查）
  - YMIR（用于实际搬运）
- 时序与责任交接：
  - 非增强基线迁移在蓝图汇报前三周完成
  - 增强从蓝图汇报后开始识别、定策略及迁移
  - 后续根据蓝图调整另行排期
  - 业务测试/新增开发由 S/4 项目开发清单另行管理；持续同步按“ECC 与 S/4 双线变更同步规则”办理责任交接
- 注释：ECC 远程 ATC 初评用于识别技术问题，迁入后按目标环境复查
- 结论：每一步都以交付物收口，进度可核对

# 02 迁移范围与对象策略

## 第 5 页｜迁移范围确定
- 导语：范围既要剔除冗余，也要避免因首次未列入而漏搬
- 判定维度（四个数据源）：
  - 使用证据：使用已有 UPL/SCMON、SUSG 聚合数据，以及作业/接口记录；优先利用 6~12 个月数据；数据不足时覆盖月结/年结等关键周期；以业务访谈和场景验证补足，不等待满一年才启动
  - 对象依赖：通过交叉引用分析静态依赖；补查动态引用与配置引用；识别上下游对象及相关依赖；将依赖展开结果纳入后续执行清单
  - 业务保留要求：结合业务部门调研，明确必须保留的业务对象与场景；考虑低频、应急和周期性用途；通过业务访谈和场景验证确认
  - 废弃候选识别：基于使用证据与依赖分析识别；零调用仅列为待确认线索；业务负责人须结合低频、应急和周期性用途确认；避免因首次未列入而漏搬
- 使用证据的两种取证策略（按甲方系统现状）：
  - 已启用审计：以已有 UPL/SCMON、SUSG 聚合数据为主，结合作业/接口记录
  - 未启用审计：以作业/接口记录、业务访谈和场景验证补足，覆盖月结/年结等关键周期，不等待满一年才启动
- 确认流程：业务部门调研 → 技术依赖扫描 → 冗余/废弃剔除 → 范围签字
- 时间分界：
  - 三周窗口（非增强对象基线）：先确认非增强对象基线；窗口前仅对扫描结果标明增强类别并隔离，不提前开展增强用途分析
  - 蓝图汇报后（增强相关工作）：增强业务识别 → 策略确认 → 迁移开展
- 统一四策略：
  - 直接迁移：保留现有对象，按范围纳入迁移
  - 重构迁移：需要调整或重构后迁移，按确认的方案执行
  - 标准功能替代：先验证功能差异，确认可被标准功能替代再纳入相应策略
  - 废弃：确认为不再使用的对象；零调用仅列为待确认线索，业务负责人须结合低频、应急和周期性用途确认
- 范围基线与变更管理：签字清单形成范围基线，依赖展开结果纳入批次执行清单；新增依赖、业务变化和剔除对象须记录原因、影响与批准人；不直接扩大范围，也不因首次未列入而漏搬
- 结论：业务签字锁定范围，技术依赖在执行清单中展开，二者分开管理

## 第 6 页｜程序对象盘点
- 导语：盘点结果清单是技术迁移的执行底账，但不作为后续 S/4 项目开发的唯一依据
- 主要对象类别（不限于）：报表（Report）｜增强（Enhancement）｜接口（Interface）｜表单（Form）｜函数组（Function Group）｜BDC｜自定义类（Class）｜Z/Y/客户命名空间表与结构｜CDS
- 同时排查的其他对象：事务码｜Query｜工作流｜表单资源｜标准修改
  - 标准修改不整段覆盖目标 SAP 标准代码，须分析业务意图后确定目标实现
- 盘点结果清单字段：
  - 识别与策略：对象编码｜对象类型｜对象描述｜模块｜业务顾问｜开发顾问｜迁移策略｜备注
  - 执行与交付：源系统/版本｜目标对象｜迁移批次｜语法检查结果｜运行入口/输入及无 Dump 记录｜交付/封存时间｜状态
- 状态定义：待迁移 → 已搬运 → 技术测试通过 → 已交付 → 已封存
- 四项说明：
  - 输出物：盘点结果清单逐对象记录四策略，确认迁移范围后形成技术迁移清单，管理搬运、技术测试与交付状态
  - 清单关系：技术迁移清单与 S/4 项目开发清单独立管理，无必须的一一对应关系，必要时仅作历史引用；已迁对象可能无后续开发，也可能对应多个开发项，开发项可覆盖多个对象
  - 增强的特殊说明：增强是程序对象的一种，策略值域与普通对象一致，但用途识别、源码分析、策略确认及迁移均在蓝图汇报后进行；前期清单仅标明“增强待蓝图后识别”，不计入三周非增强交付量
  - 配套资产纳入正式范围：程序选择变式、ALV 布局、后台作业、自开发表数据；并排查 TVARVC、权限、RFC/逻辑系统/IDoc 配置、服务激活、文件路径和输出设备；逐项明确迁移/重建/验证责任，源码迁移不等于环境与数据已就绪；abapGit 表数据功能是否被 YMIR 集成，以实际版本验证为准
- 结论：每个对象都有策略、批次、技术测试记录和状态，模块顾问可按模块查看本模块对象去向

# 03 迁移工具 YMIR 与 YENH

## 第 7 页｜批量迁移工具 YMIR 架构
- 导语：YMIR 为自研工具，非 SAP 官方标准工具；事务代码 YMIR，描述“跨系统在线迁移程序对象”
- 技术底座：abapGit（对象序列化/反序列化）＋ ABAP RFC（跨系统在线传输）
- 支持范围：形成“本项目对象类型 × YMIR 当前版本”的支持与实测矩阵，包含自动覆盖、补充处理和例外责任人；不按 abapGit 支持清单等同于所有类型全覆盖
- 交接材料列举的覆盖对象：PROG｜FUGR｜CLAS｜INTF｜DOMA｜DTEL｜TABL｜TTYP｜VIEW｜SHLP｜ENQU｜MSAG｜SSFO｜FORM｜ENHO｜DDLS
  - 各类型及子对象、目标版本适用性按试迁确认
- 迁入原则：优先处理 DDIC 等基础依赖，再处理 ABAP 对象与翻译；按实际依赖与激活阶段执行；循环依赖/失败项单独处理；不按简单三段顺序视为所有对象的固定算法
- 迁移管理：本项目资产哪些自动覆盖、哪些需补充处理有清单；每批有源版本、目标状态和差异报告；全部差异均有处置结论
- 四大迁移能力：在线迁移（RFC 在线抽取）｜按需迁移（按范围清单选择）｜递归展开迁移（依赖展开与补查）｜一键迁移（包/对象集批量执行）
- 结论：工具能力决定搬运效率，支持矩阵与差异报告决定完整性

## 第 8 页｜YMIR 四大特性
- 导语：四项特性分别解决“怎么取、取什么、取全、取快”
- 四大特性：
  - 在线迁移：直连源 ECC 用 RFC 在线抽取，免离线导出/导入
  - 按需迁移：按范围清单选择性迁移，不搬冗余代码
  - 递归展开迁移：基于 Where-used/交叉引用展开 INCLUDE、函数组、DDIC、屏幕、消息类、类等依赖；验证“对象依赖谁”的展开方向、索引有效性与循环处理；动态 CALL FUNCTION/SUBMIT、配置中的对象名及外部入口通过运行证据、配置检查与场景验证补查
  - 批量迁移：对包/对象集一键批量执行
- 三周批次边界：
  - 递归展开后核对增强对象与共享对象中的增强实现，增强不得因整包选择或依赖展开提前迁移
  - 可分离的基础依赖先处理，强耦合异常明确负责人和处置计划，不自动扩大三周范围
- 结论：递归展开保证依赖不漏，批次边界保证三周范围不被增强和异常撑大

## 第 9 页｜YMIR 批次执行与异常处理
- 导语：每个批次都有报告、状态和异常关闭证据
- 批次执行流程：批次清单与源版本确认 → 依赖/同名对象预检查 → YMIR 搬运 → 激活与目标检查 → 源目标差异对账 → 异常关闭
- 批次报告字段：计划对象｜展开依赖｜成功/失败/跳过对象｜激活状态｜语法检查结果｜运行入口与无 Dump 记录｜源版本及责任人
- 批次状态定义：已搬运（已通过 YMIR 完成搬运）｜技术测试通过（已完成激活、语法检查，且运行无 Dump）｜已交付（完成技术交付）｜已封存（技术交付完成并封存）｜待验证（待后续验证，不以业务验证计迁移完成率）
- 时间标记与范围：批次区分“蓝图前三周非增强基线”与“蓝图后增强”；后续蓝图调整属于项目开发清单，ECC 增量属于持续同步台账，均不混入已封存的技术迁移批次
- 异常处理规则：
  - 断连/失败先核对目标实际状态，再按依赖重跑未完成项；重跑不得重复覆盖已适配对象
  - 同名对象先比较再决定，已修改对象进入“双线同步执行与冲突处理”合并流程
  - 不支持类型转明确的补充迁移方式
  - 失败项逐项有负责人和关闭证据
- 技术交付路径：核对 ECC 有效源版本 → S/4 目标开发环境接收与必要适配 → 语法检查与运行无 Dump → 交付并封存；后续测试/生产发布由实现项目按传输流程负责，保留版本与请求用于历史追溯
- 注释：日志、预检查、定向重跑等自动化程度须经 YMIR 演示验证，未实现功能由台账、人工比较及受控重执行补齐
- 结论：批次的可信度来自差异对账和异常关闭

## 第 10 页｜ECC 与 S/4 双线变更同步规则
- 导语：ECC 运维持续进行、S/4 项目开发持续进行，两边的变更必须用同步队列管住
- 同步链路（三段）：
  - ECC 发布节点：变更单创建时登记与评估 → 开发期间提前评估 → 生产发布后核实实际生效的版本，进入同步队列
  - 同步队列：每项有效变更都要有 S/4 去向，按业务需要同步其意图和必要实现，不能把 ECC 全对象覆盖到 S/4
  - S/4 批次：按批次安排适配/合并/传输与测试 → 关联目标实现和验证证据，完成后进入后续承接
- 纳管范围：ECC 首轮源基线之后至最终切换基线之间的新增、修改、删除、回退，覆盖源码/增强、配置/变式/作业及会影响迁移范围的数据结构变化；S/4 对已迁对象的修改同样记录，便于识别双边冲突
- 与迁移结项衔接：非增强在前三周、增强在蓝图后分别完成技术迁移和交付；迁移清单按批次完成后封存；双线台账独立延续，交付后的 ECC 修改由实现项目承接，需开发的登记为项目开发项；增强前期变更仍仅登记留痕
- 触发规则：ECC 生产发布后核实实际生效版本，未投产内容不默认当作有效基线；紧急变更可先保障 ECC，再按紧急机制立即补登/评估；冻结窗口内不得遗漏任何批准例外
- S/4 处置结论（独立于四迁移策略）：
  - 需同步：新系统继续使用且差异尚未实现；评估依赖和蓝图影响后安排适配/合并、传输与测试
  - 已覆盖：S/4 标准或项目实现已满足同一需求；关联目标实现和验证证据，不能只凭口头判断关闭
  - 不适用：ECC 专用临时处理或目标业务已取消；记录理由，由业务负责人和目标技术负责人确认
  - 待决策：蓝图、范围或影响尚不明确；设置责任人与决策截止点，不能按“无需同步”关闭
- 节奏与责任：建议每工作日对账，每周展示待评估/待同步/冲突/待验证及逾期项；迁移期间由迁移团队协调，交付时指定 S/4 项目接管人
- 两类关闭：技术迁移按语法无错误、运行无 Dump 完成并封存；持续同步项按当前归属流程关闭，项目承接后的业务验证和切换安排由实现项目负责，不构成重开迁移清单的条件
- 结论：迁移清单封存不等于停止同步，双线台账独立延续

## 第 11 页｜双线同步执行与冲突处理
- 导语：迁移期以技术测试为完成标准；交付后的同步开发及后续测试问题进入 S/4 项目开发清单
- 七步执行：登记 ECC 变更 → 判断适用性及承接团队 → 比较版本与依赖 → 适配/合并 → 目标传输 → 按归属流程验证 → 核对证据关闭
- 三版本合并关系：
  - E0：上次已接收的 ECC 源版本（首次同步用初始搬运源快照）
  - E1：本次 ECC 有效版本
  - S：当前 S/4 版本
  - 做法：比较 E0→E1 的差异，再结合 S/4 已有适配和新开发合入业务意图，形成目标版本；比较期间发生新修改则重新比较
- 冲突规则：即使 S/4 近期未改，也先判断是否仍与 ECC 兼容｜S/4 已适配、已重构或功能拆分时由开发合并，不能直接覆盖｜共享依赖、删除/回退、配置与数据结构变化须重新做影响分析｜代码无冲突不代表业务无冲突
- 工具分工：YMIR 承担已验证范围内的对象搬运；同步判断、版本快照/比较、冲突合并与批准由项目流程及已验证工具完成；不假定 YMIR 自动三方合并；必要时采用版本导出、差异工具、手工适配和 CTS 传输
- 项目承接后的切换控制：实现项目核对最终 ECC 增量、批准冻结例外并安排所需回归与发布；保留原版本比较和防覆盖规则；这是项目持续同步管理，不延长已交付对象的技术迁移生命周期
- 证据链与记录要求：ECC 变更单/有效版本 ↔ 目标实现/传输记录 ↔ 对应处理与测试记录；历史迁移记录仅按需引用；技术迁移证据只保存技术测试证据；项目承接后的同步开发和业务回归由项目记录，验证后推进当前同步基线，不改写封存的迁移清单
- 结论：同步靠版本比较和证据链，不靠工具覆盖

## 第 12 页｜增强盘点与策略识别（YENH · ECC 端）
- 导语：自研工具 YENH 部署在 ECC 与 S/4 双端；增强不属于蓝图前三周非增强对象迁移范围
- YENH 定位与开展时间：蓝图汇报之后，由业务与技术顾问结合项目蓝图开展增强用途识别、源码分析、策略确认及后续迁移
- ECC 增强代码现状：“巨石”代码——一个出口里堆叠多段业务逻辑、冗余重复，无法直接判断去向
- 识别原则：不能只看名字定策略，须阅读与业务有关的实现并确认触发路径；按复杂度和风险安排阅读深度，不把所有增强全面拆分作为迁移前提；特殊实现和标准修改另作补查
- ECC 端分析动作与协同：
  - 盘点识别：业务/技术顾问借助 YENH 确认用途、适用范围与触发条件
  - 形成清单：形成增强功能点清单
  - 策略处理：稳定实现先作技术迁移；为迁入所必需的技术处理留在迁移批次，按新业务规则进行的拆分、重构和功能调整登记为 S/4 项目开发项
  - 紧密协同：业务顾问确认功能是否在用，技术顾问确认代码兼容性
- 增强类型与扫描覆盖：Customer Exit（CMOD/SMOD）｜BAdI｜隐式增强点｜User Exit｜BTE（业务交易事件）｜VOFM 例程｜Field Exit｜Enhancement Spot；交接材料列举的增强类型须形成扫描覆盖矩阵
- 重点风险：隐式增强点随源码改动会位置漂移甚至失效，YENH 需单独标记，作为识别重点
- 功能点清单拆解示意：增强对象清单（YENH 盘点）→ 用途识别（阅读实现与触发路径）→ 增强功能点清单（按复杂度和风险确定阅读深度）→ 逐项策略（直接迁移｜重构迁移｜标准功能替代｜废弃）
- 注释：巨石代码拆解仅是功能点分析示意，不表示 YENH 自动全面拆分；全部增强用途识别在 T0 蓝图汇报之后
- 结论：增强由业务顾问与技术顾问共同识别，迁移只做必需的技术处理

## 第 13 页｜增强全景管理（YENH · S/4 端）
- 导语：迁移到 S/4 后，YENH 以已确认的增强/功能点清单为基础管理；功能点独立开关以完成必要代码接入、依赖分析和测试为前提，不等于旧巨石代码自动拆分
- 开展时间：蓝图汇报后完成增强识别、技术迁移和语法/运行测试；增强业务效果验证及按蓝图调整由 S/4 实现项目管理
- 四项能力：全景管理（所有增强一屏可见）｜元数据管理（增强点位置/类型/归属）｜启动条件管理（按条件启停）｜按原子增强功能点开关（每个功能点独立启停）
- 元数据字段：增强点位置｜增强类型｜归属｜用途｜责任人｜启停状态
- 价值与衔接：
  - 可追溯：增强位置、用途、责任人与启停状态可追溯
  - 迁移技术测试记录：记录实际调用/触发路径、语法检查和无 Dump 结果
  - 业务验证与问题管理：业务条件、重复处理及业务结果的验证属于项目测试，发现的问题列入开发清单；开关管理不直接等同于 Clean Core
  - 与 ATC/AI 衔接：YENH 识别的增强清单作为 ATC 检查与 AI 修复的输入
- 注释：管理概念示意，非真实界面
- 结论：S/4 端的 YENH 让增强位置、用途和启停状态可追溯

# 04 S/4 适配检查与结果修复

## 第 14 页｜ATC 适配检查
- 导语：ATC 用于定位必要技术修复，不能把全部高优先级建议、业务正确性、性能优化或 UAT 作为技术迁移结项门槛
- 五步执行流程：
  - 选定变式：按目标 S/4 版本与检查系统能力选定 ATC 变式/简化数据库；S4HANA_READINESS_2025 仅在目标及检查环境匹配时采用
  - ECC 远程初评：在 ECC 上远程执行 ATC 初步检查，识别潜在问题，明确后续分析范围
  - 按范围分析：按业务与技术范围分析，结合检查优先级和业务影响分类处理
  - 迁入后目标检查：在目标系统执行 ATC，验证修复效果，识别剩余问题
  - 修复复查：针对问题进行技术修复，重新执行 ATC 确认已解决
- 时间安排：蓝图前三周（非增强基线对象的检查、必要技术修复与复查）｜蓝图后识别/迁移阶段（增强的对应检查）｜另行排期（蓝图方案引起的后续业务调整与回归）
- 检查项与验收条件：Field Extension｜Search DB Operations｜简化对象用法｜DDIC 增强｜视图基表——按 ATC 检查结果处理，满足技术完成标准；S/4 语法错误——语法检查无错误，记录的运行路径无 Dump
- 结果分级与处理：
  - 按检查优先级和业务影响共同处理
  - 误报经技术复核后使用适用豁免/伪注释，留存原因、批准人及复查条件，不靠抑制消息制造“清零”
  - _NO_FLE / _REMOTE 等变式的可用性、检查范围及遗漏风险须按检查系统核验，不与目标版本变式无条件互换
  - 非阻断的业务/优化事项转项目开发清单管理
- 技术完成标准：语法检查无错误，记录的运行路径无 Dump
- 结论：ATC 结果服务于必要技术修复，技术完成标准保持不变

## 第 15 页｜ATC 结果修复——ADT Quick Fix
- 导语：Quick Fix 按实际 ATC finding 的标记与版本条件选择，不表示相关业务变化都能一键解决
- 操作流程：打开问题列表（ATC Problems View）→ 触发 Quick Fix（选择灯泡标记，Ctrl+1，从列表中选择合适的 quick-fix）→ 保存激活并复查（再次运行 ATC）
- 可修复项清单（检查类型 → 是否可能提供修复）：排序相关 → 可能｜字段长度相关 → 可能｜数据访问相关 → 可能｜其他检查项 → 视具体检查而定
- 适用范围：排序、字段长度、数据访问等检查可能提供修复，不表示 MATNR、KONV/BSEG/VBFA/VBUK/VBUP 等相关业务变化都能一键解决
- 批量执行注意事项：
  - 仅对支持 mass-enabled 的修复批量执行（参考 Note 2738251、2364938，应用前核验适用性）
  - 先保存版本、选小批次验证，再扩展并复查语法及运行无 Dump
  - 后续业务回归归实现项目
- 结论：Quick Fix 适合有规律的问题，批量使用必须先验证、可复查

## 第 16 页｜AI 辅助适配——总体方案
- 导语：未启用 AI 也可按 ATC / Quick Fix / 人工流程交付
- 两条路线对比（使用位置/连接方式｜底层模型/外部代理｜主要能力）：
  - 路线 A SAP 原生（SAP Joule for Developers 的 ABAP AI）：内嵌在 ADT 中｜SAP-ABAP-1｜面向 ABAP 开发的代码解释、问题分析与修复建议
  - 路线 B 外部 Agentic：通过 ADT MCP Server 将 ABAP 工具暴露成 MCP｜GitHub Copilot、Amazon Q 等外部 AI agent 可驱动｜在外部 AI agent 协同下进行 ABAP 代码解释、问题分析与修复建议
- 关键说明与限定：
  - 两条路线作为解释与修复的可选加速手段
  - 启用前核实目标版本、许可、ADT/MCP 环境、连接与代码使用要求
  - 用代表性修复对比人工耗时、采用率和复查结果，未验证前不承诺节省比例
- 结论：AI 先验证再使用，不改变交付标准

## 第 17 页｜SAP Joule ABAP AI 能力
- 导语：交接材料列出的能力需按版本、许可和环境逐项确认
- Custom Code Migration AI Assistant：Explain ATC finding（解释 + 步骤建议）｜Code proposal（生成修复代码）
- 配套能力：Code Explain / ATC Explain｜Predictive Code Completion｜ABAP/CDS Code Explanation｜Unit Test Generation｜Documentation Chat（/docs）
- 关键说明：
  - 版本范围：交接材料涉及 Private Edition 2021~2025，实际功能覆盖须逐项核验，不将整个版本区间视为同等可用
  - 许可与环境：Joule 相关能力还须确认附加许可与环境条件
- 本项目可用性确认表：7 项能力 × 目标版本｜许可要求｜环境条件｜本项目可用性，当前全部“待核验”
- 结论：可用性确认表完成前，不把 Joule 能力计入交付计划

## 第 18 页｜外部 Agentic 迁移路线
- 导语：GitHub Copilot / Amazon Q 作为当前端，驱动“ATC 检查 → 确定性 quick-fix → AI 修复”
- MCP 架构：AI 助手（GitHub Copilot、Amazon Q）→ 通过 MCP 调用 ABAP 工具 → ADT MCP Server（将部分 ABAP 工具暴露为 MCP）→ ABAP 工具（ATC 检查、确定性 quick-fix、AI 修复）→ 目标系统 S/4HANA（Custom Code Migration Agent 分析与修复建议）
- 候选修复流程（human-in-the-loop）：提案生成 → 人工复核 → 技术测试（在测试环境验证）→ 受控接收（纳入受控版本）→ 结果审查（结果落 CSV 导入 Excel 逐条审）
- 规则：
  - 工具置信度用于候选修复分流，不替代正确性判断；候选代码在开发环境生成，人工复核后才进入受控版本和测试
  - 复核通过的候选代码进入测试，测试通过后进入受控版本
  - 低置信度/报错保留为提案，不自动发布
  - 自定义指令用 Note 3751537（Copilot）、3751829（Amazon Q）
- 注释：交接材料中的“Q2 2026 GA”不能直接作为本项目可用性承诺，须按当前正式文档与目标环境验证
- 结论：AI 产出的是提案，版本准入由人工复核和技术测试决定

## 第 19 页｜AI 适配校验与风险防控
- 导语：AI 辅助加速必要技术修复，技术测试通过后完成迁移交付
- 三道技术校验：
  - 人工复核代码差异与适用简化项：明确需要调整的内容及适用范围
  - 语法检查：修复语法错误，确保满足目标环境的语法要求
  - 运行无 Dump：完成运行测试，记录实际测试入口与输入；不据此宣称业务结果均正确
- 风险矩阵（概率 × 影响）：具体风险项待项目评估
- 应用门槛与风控原则：
  - AI 提案经代码复核及上述技术测试后纳入迁移版本
  - 置信度不能代替语法和运行检查
  - AI 提案仅作起点、关键测试用例锁死、禁止批量盲套
  - 后续业务回归发现的问题统一进入 S/4 项目开发清单
  - 业务规则验证、后续调整与上线决策由实现项目管理
- 结论：AI 不改变技术完成标准，也不承担业务正确性判断

# 05 附加资产、工作量与案例

## 第 20 页｜其他程序对象迁移
- 导语：这些资产缺失会直接影响上线即用，逐项明确方法与责任人
- 四类资产（缺失影响 → 环境依赖）：
  - 程序选择变式（报表运行的个性化参数）：报表缺筛选变式要重配，否则影响上线即用 → 关联 TVARVC 等环境依赖
  - ALV 布局（报表展示的个性化布局）：ALV 缺布局要重调，否则影响上线即用 → 关联运行用户/权限等环境依赖
  - 后台作业（定时执行的业务处理）：定时作业缺了要重设，否则影响上线即用 → 关联运行用户/时间/前后置关系、连接、路径、打印资源
  - 自开发表数据记录（业务数据的历史记录）：历史数据丢了无法对账；与变式/作业迁移并列，按测试准备与切换需求安排加载，不作为独立数据迁移章节
- 资产 — 迁移/重建方式 — 责任人 — 验证结果：
  - 程序选择变式：由 YVAR 已验证扩展、配套脚本或目标端重建完成，变式值按目标环境调整｜明确责任人｜由实现项目验证
  - ALV 布局：由 YVAR 已验证扩展、配套脚本或目标端重建完成｜明确责任人｜由实现项目验证
  - 后台作业：由 YJOB 已验证扩展、配套脚本或目标端重建完成，作业用户/时间/前后置关系及接口端点按目标环境调整｜明确责任人｜由实现项目验证
  - 自开发表数据记录：由 YTBC 已验证扩展、配套脚本或目标端重建完成，按测试准备与切换需求安排加载｜明确责任人｜由实现项目验证
  - 环境依赖（关联项）：TVARVC、运行用户/权限、连接、路径、打印资源等，详见盘点结果清单｜明确责任人｜由实现项目验证
- 关键说明：测试环境禁止误连生产或提前释放生产作业；技术交付保留迁移与技术执行记录，切换首次执行及业务结果由实现项目验证
- 结论：配套资产与程序一起交付，才能做到上线即用

## 第 21 页｜自定义表数据迁移功能
- 导语：自定义表数据迁移是与变式、ALV 布局和后台作业并列的配套能力，支持多线程
- 流程概念：选择表与范围 → 执行 → 日志 → 对账
- 五个要点：
  - 功能定位：支持将需保留的自定义表数据按确认范围带到 S/4；本页不展开项目级主数据/交易数据迁移方案
  - 结构与内容分开：自定义表结构按 YMIR 支持矩阵随非增强对象迁移；表内数据由 YTBC 处理
  - 操作流程：选定自定义表与数据范围 → 核对目标表结构/字段映射及 client → 执行数据迁移 → 查看日志与结果 → 对账确认；简单兼容的 Z 配置表数据可纳入同一功能，目标专用值按项目规则调整
  - 执行控制：迁移前确定同主键数据的跳过/更新规则和可恢复方式，保留处理日志；失败与重跑先核对目标实际数据，避免重复写入或覆盖目标有效维护；工具具体选项与自动化程度以真实界面和演示为准
  - 交付与后续范围：保留范围、执行日志、记录数与关键字段/主键对账，完成该配套功能的技术交付；后续业务口径核验及由此产生的调整纳入实现项目，不扩展为整个业务数据测试专项
- 结论：自定义表数据以记录数与主键对账完成技术交付

## 第 22 页｜工作量评估

# 06 里程碑与总结

## 第 24 页｜里程碑与落地保障
- 导语：两类批次分别结束，全部范围交付后专项清单归档，不等到 UAT 或上线才结项
- 技术迁移里程碑：
  - 范围/源版本与环境就绪：明确迁移范围，确认源版本与环境就绪
  - 分批技术迁移：非增强蓝图前三周、增强蓝图后，两类批次分别推进
  - 技术测试：语法检查无错误，运行无 Dump
  - 交付：批次通过技术测试后交付给业务顾问进行测试
  - 清单封存：两类批次分别结束，全部范围交付后专项清单归档
- 三类台账（定位｜主要内容｜责任分工｜封存/处理规则）：
  - 技术迁移清单（批次交付后封存）：记录本次技术迁移的批次交付成果｜对象/版本、语法检查、运行入口/输入及无 Dump 记录｜迁移团队负责范围、搬运、必要技术修复和技术测试，交付时指定 S/4 项目接管人｜记录交付人、接管人和封存时间；业务测试未结束不阻止已通过技术测试批次的封存
  - S/4 项目开发清单（承接后续问题）：承接后续问题与业务变化的开发清单｜后续问题、业务变化的开发项｜由项目负责人协调开发、测试与发布｜后续问题新建项目开发项，可引用历史记录但不要求关联，不重开迁移清单
  - ECC 双线台账（持续延续）：ECC 双线期间持续延续的台账｜ECC 双线相关的变更与问题｜由项目负责人协调开发、测试与发布｜在 ECC 双线期间持续延续
- 结论：技术迁移按节点结项，后续问题和双线变更都有明确承接台账

## 第 25 页｜总结
- 导语：回到甲方关心的问题——优质二次开发资产能否按时按质迁到 S/4
- 四个结论：
  - 范围可控：范围基线 + 业务功能/技术资产映射 + 四策略；新增依赖与变更有批准记录，每项资产有去向与负责人
  - 完整性可核对：YMIR 批量搬运与递归依赖展开，加动态/配置引用补查、配套资产验证和源目标差异对账；不以工具能力代替完整性证据
  - 技术迁移完成：非增强蓝图前三周、增强蓝图后完成技术迁移；语法检查无错误、实际测试路径运行无 Dump 即完成技术测试，交付后封存迁移清单，不代表全部业务测试完成
  - 后续开发统一管理：技术搬运不是工作量大头，主要投入在后续业务规则调整及修改；后续测试问题和需开发的 ECC 变更进入 S/4 项目开发清单，双线台账独立延续，不重开已封存的迁移清单
- 结论：按时靠 T0 前后两条线分开推进，按质靠统一的技术测试标准与差异对账，业务层面由 S/4 实现项目统一承接
